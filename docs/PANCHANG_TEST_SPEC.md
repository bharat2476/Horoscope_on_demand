# Panchang accuracy test specification

Status: draft, waiting for provider approval. No provider is called by this repository yet.

This specification defines how a candidate calculator will be compared with an independent reference. Agreement with a popular website is not a pass. A provider is accepted only when its output matches the convention written here, inside the tolerances written here, on the date set generated by that same convention.

The normalized record is [`panchang-normalized.schema.json`](panchang-normalized.schema.json). Every reference row and every provider row is stored in that shape. The app's current `getPanchang` function stays unavailable until a provider is approved and this test has a recorded result.

## Reference convention

The reference is a written calculation, not a second website.

| Item                         | Convention                                                                                                                                                                                                                                            |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Time zone                    | `Asia/Kolkata` for all five cities. Indian Standard Time has no daylight-saving transition.                                                                                                                                                           |
| Instant                      | ISO-8601 with a numeric offset. For these cities the offset is `+05:30`.                                                                                                                                                                              |
| Place                        | WGS84 latitude, longitude, and elevation pinned from a cited gazetteer before the run. The city ids in the app (`gj-ahmedabad`, `mh-mumbai`, `up-varanasi`, `tn-chennai`, `wb-kolkata`) have no coordinates and are labels only.                      |
| Ayanamsa                     | Lahiri (Chitrapaksha), the reckoning used by the Rashtriya Panchang of the Positional Astronomy Centre, Kolkata. Record the numeric ayanamsa, in arcseconds, at each test instant.                                                                    |
| Longitudes                   | Geocentric apparent ecliptic longitudes of the Sun and Moon. Sidereal longitude is tropical longitude minus the Lahiri ayanamsa.                                                                                                                      |
| Tithi                        | Elongation `(Moon − Sun) mod 360`. One tithi is 12°. Thirty tithis. Amavasya is the tithi that ends at elongation 0°. Purnima is the tithi that ends at elongation 180°.                                                                              |
| Nakshatra                    | Sidereal lunar longitude divided into 27 equal parts of 13°20′. Pada is a quarter of a nakshatra, 3°20′, and is recorded when the provider returns it.                                                                                                |
| Yoga                         | `(sidereal Sun + sidereal Moon) mod 360`, divided into 27 equal parts of 13°20′.                                                                                                                                                                      |
| Karana                       | Half a tithi, 6° of elongation, using the movable and fixed karana sequence. The sequence used in the reference generator is written into the test log before the run.                                                                                |
| Day boundary                 | Sunrise to the next sunrise at the same coordinates. The name in force at sunrise is the name of the day. Every later boundary before the next sunrise is a transition.                                                                               |
| Sunrise and sunset           | Upper limb of the Sun, standard atmospheric refraction, elevation as pinned. A second reference column uses the middle of the solar disk, because that choice moves the clock time by minutes and moves every interval that is a fraction of the day. |
| Rahu Kaal, Yamaganda, Gulika | One eighth of the upper-limb sunrise-to-sunset interval. The weekday segment table is fixed in the test log before the run. These intervals move when the sunrise convention moves.                                                                   |
| Month system                 | Both Amanta and Purnimanta are computed for festival-rule rows. A row names which system it uses.                                                                                                                                                     |

Classical element widths are the reference rules. They are not copied from a provider response.

## How the reference is verified

Three checks are independent of each other. A provider does not become the reference by agreeing with another provider.

1. **Astronomical check.** Sun and Moon longitudes come from a local Swiss Ephemeris test harness, Lahiri mode (`SE_SIDM_LAHIRI` in the Swiss Ephemeris programming documentation). The harness is a private test tool. It is not shipped in the Android app, and it is not an AGPL release of this product. The element boundaries are then produced by the widths in the table above. Swiss Ephemeris publishes its own comparison of Lahiri values with the Indian Astronomical Ephemeris in Appendix E of its programming documentation. That appendix is Astrodienst's comparison, and this project rechecks the test year against the purchased ephemeris in step 2.
2. **Published-almanac check.** A tester transcribes, by hand, a small subset from the Positional Astronomy Centre publications bought for the test year: the Indian Astronomical Ephemeris and the Rashtriya Panchang. The IMD describes the Rashtriya Panchang as giving sunrise, sunset, moonrise, and moonset for four metropolitan cities, plus tithis, nakshatras, yogas, and nirayana longitudes. Mumbai, Chennai, and Kolkata are in that metropolitan set. Ahmedabad and Varanasi are checked against the astronomical reference when the printed book has no table for them. The transcription records the book's stated limb, ayanamsa, and time scale. It is not scraped.
3. **Drik Panchang is not an input.** Drik Panchang publishes useful method pages, including upper-limb versus middle-limb sunrise. Those pages may be read. Their calculated tables are not copied into this repository, the test log, or the app. `robots.txt` on `www.drikpanchang.com` disallows `/dp-api/`. No private endpoint is called.

The reference generator writes one normalized JSON document per city-date. The provider adapter writes another. The comparison reads those two documents. It does not read a website during the assertion.

| Kolkata   | `wb-kolkata`   | 22.5726 N            | 88.3639 E             |

Elevation is recorded per city. If the gazetteer elevation is missing, the run uses `0` and sets `elevationMeters` to `0`, and a second column is computed at the gazetteer elevation when it arrives. A provider that cannot accept elevation is marked `elevationMeters: null` and is not failed only for that omission.

## Date set

The window is the civil year that contains a full set of lunar months after approval. The first proposed window is 2026-04-01 through 2027-03-31 in `Asia/Kolkata`. Dates are chosen by the reference generator, not by copying a festival calendar.

For each city, select at least 30 dates:

| Class                | Count | Selection rule                                                                                                                                                                                                                                  |
| -------------------- | ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary             | 10    | No tithi or nakshatra boundary within two hours of sunrise. Spread across the window.                                                                                                                                                           |
| Tithi transition     | 4     | A tithi ends within 30 minutes of sunrise.                                                                                                                                                                                                      |
| Nakshatra transition | 4     | A nakshatra ends within 30 minutes of sunrise.                                                                                                                                                                                                  |
| Amavasya             | 4     | Amavasya is the tithi in force at sunrise. Include one date from each quarter of the window when the generator can do so.                                                                                                                       |
| Purnima              | 4     | Purnima is the tithi in force at sunrise. Same seasonal spread.                                                                                                                                                                                 |
| Ekadashi             | 4     | Two Shukla Ekadashi and two Krishna Ekadashi, each in force at sunrise.                                                                                                                                                                         |
| Named solar ingress  | 2     | The instants when sidereal solar longitude crosses 0° (Mesha) and 270° (Makara). The civil date is the date of that instant in `Asia/Kolkata`. These two dates are the same instant nationwide; each city still gets its own sunrise-based row. |

That is 32 city-rows before the shared ingress rows are deduplicated, which stays above 30 per city. Additional disputed festivals, including regional new-year days and festivals whose Amanta and Purnimanta dates differ, go on the convention sheet. They are not added to the pass count until a written rule for that festival is attached to the row.

Each selected row stores the rule id (`ordinary`, `tithi-near-sunrise`, `nakshatra-near-sunrise`, `amavasya`, `purnima`, `ekadashi-shukla`, `ekadashi-krishna`, `mesha-sankranti`, `makara-sankranti`) and the reference boundary instant that caused the selection.

## Tolerances

Times are compared after both sides are converted to UTC.

| Quantity                                                      | Pass                                              | Record, do not fail                                                                  | Fail                                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Sunrise or sunset, same limb, same elevation, same refraction | Absolute difference ≤ 60 seconds                  | Difference ≤ 3 minutes while limb or elevation is `unspecified`                      | Difference > 3 minutes, or > 60 seconds after the limb and elevation are known and aligned |
| Tithi, nakshatra, yoga, or karana boundary                    | Absolute difference ≤ 2 minutes                   | Difference > 2 minutes and ≤ 10 minutes                                              | Difference > 10 minutes                                                                    |
| Rahu Kaal, Yamaganda, Gulika                                  | ≤ 60 seconds after sunrise and sunset have passed | The whole interval shifts by the same sunrise error, within 60 seconds of that shift | A different eighth of the day, or a shift that is not explained by the sunrise difference  |
| Element name at a time more than 10 minutes from a boundary   | Names match                                       |                                                                                      | Names differ                                                                               |
| Element name within 10 minutes of a boundary                  |                                                   | Record both names and both instants                                                  |                                                                                            |

A close boundary is a convention or rounding record. It is not counted as evidence that either side is accurate.

## Convention differences

These are stored on the row and excluded from the fail count:

- Upper limb versus middle limb.
- Elevation used versus elevation ignored.
- Standard refraction versus no refraction.
- Lahiri versus Lahiri-ICRC, Raman, KP, or tropical. A provider that cannot select Lahiri fails the convention check before the date run.
- Amanta versus Purnimanta month name.
- Tamil or Bengali traditional arithmetic (`vakya` / Surya Siddhanta) versus drik longitudes. The MVP reference is drik longitudes. A traditional row is a separate labeled sample, not a failure of the drik reference.
- Weekday segment tables for Rahu Kaal when the provider documents a different table. The table is attached to the row. An undocumented different table fails.

The comparison report has two sections: `same-convention` and `recorded-difference`. Only `same-convention` can reject a provider.

## Provider rejection

Reject the provider for the MVP if any of these is true:

1. The published request cannot set latitude, longitude, and an ISO-8601 instant with a numeric offset.
2. Lahiri cannot be selected, or the documentation does not say which code is Lahiri.
3. More than 5 percent of ordinary-date tithi names, or ordinary-date nakshatra names, disagree with the reference away from a boundary.
4. Any Amavasya, Purnima, or Ekadashi name at sunrise disagrees when the reference boundary is more than 10 minutes from sunrise.
5. Sunrise or sunset fails the aligned tolerance on more than two dates in any one city.
6. Any same-convention element boundary is more than 10 minutes from the reference on more than two dates in the whole set.
7. The provider returns a normal Panchang body for a date outside the range it documents, checked at year 1800 and year 2200, instead of a documented error.
8. More than 1 percent of the test calls time out, return an undocumented error, or exhaust the quota that was funded for the test.
9. The terms forbid commercial display in this app, forbid a 24-hour cache of a city-date, or require the Android client to hold the API secret.
10. The terms forbid keeping the test log for the period needed to audit the decision.

A failure on one element rejects that element. The provider can still be accepted for a narrower contract, for example sunrise and tithi only, if the failed element is removed from the product. Rahu Kaal is in the MVP product, so a Rahu Kaal failure rejects the MVP candidate.

## Historical dates, errors, and uptime

Add these probes once per provider, not once per city:

- One date in 1900, one in 1970, one in the test window, one in 2100, and one date outside any range the provider states.
- One malformed coordinate, one missing offset, and one unknown ayanamsa code.
- Record HTTP status, provider code, and whether the body can be mistaken for a real Panchang.

Uptime is whatever the contract states. A marketing target is recorded as a target. A test of a few hundred calls does not establish a monthly uptime percentage.

## What the test must not do

- Scrape Drik Panchang or call a path disallowed by its `robots.txt`.
- Treat a match with Prokerala, DivineAPI, Vedika, or any other vendor as the definition of correctness.
- Invent a festival date to fill a quota. The generator selects dates from the reference rules.
- Store birth date, birth time, or birthplace. This test is a city and a civil date.
- Put provider secrets in the app or the repository.

## Exit

The test log names the provider, the plan, the credit cost of the run, the git revision of the reference generator, the Swiss Ephemeris version, the gazetteer citation, and the pass or fail under the rules above. That log is the evidence for the approval decision. Until it exists, the app continues to return `status: 'unavailable'`.

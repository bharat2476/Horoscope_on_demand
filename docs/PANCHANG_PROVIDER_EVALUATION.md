# Panchang and horoscope provider evaluation

Reviewed on 14 October 2026 from published documentation and terms. No provider was called. No paid plan was purchased. Prices and quotas change, so the links below have to be opened again before an order.

This is a recommendation for approval. It is not an accepted product decision, and it does not connect the app. The Android client still returns an unavailable Panchang and an unavailable horoscope.

The normalized record is [`panchang-normalized.schema.json`](panchang-normalized.schema.json). The acceptance test is [`PANCHANG_TEST_SPEC.md`](PANCHANG_TEST_SPEC.md).

## Recommendation

Use **Prokerala** as the MVP candidate for Panchang numbers, on a paid plan, only after the test specification passes and the terms are accepted in writing.

Use these published operations, with `ayanamsa=1` (Lahiri):

- `GET /v2/astrology/panchang` for vaara, tithi, nakshatra, yoga, karana, sunrise, sunset, moonrise, and moonset, including start and end times when an element changes.
- `GET /v2/astrology/inauspicious-period` for Rahu, Yamaganda, Gulika, Dur Muhurat, and Varjyam.

Keep the call on a server the project controls. Cache a city-date for at most 24 hours, which is the maximum the terms allow unless Prokerala agrees a longer period in writing. Delete stored responses if the account ends. The phone stores the selected city id, not the provider payload.

Do not use Prokerala's daily horoscope text for the MVP. The published daily-prediction operation returns English prose for a Western sign name, costs 250 credits per request, must be refreshed at least every 24 hours, and must be deleted when the account ends. That cycle does not leave room for the review this app requires before a prediction is shown. Horoscope text stays unavailable until a separate text license is approved.

**Fallback.** If Prokerala fails the test, or the contract is refused, calculate positions with the **Swiss Ephemeris Professional License** (not the AGPL edition) and apply the rules in the test specification. That library does not return a finished Panchang. Tithi, nakshatra, yoga, karana, and Rahu Kaal still have to be implemented from those rules and checked against the Rashtriya Panchang. The AGPL edition is the wrong license for a closed-source Play app and for a private server.

**Drik Panchang** (`www.drikpanchang.com`, Adarsh Mobile Applications LLP) is a method reference. It is not a data provider. No public commercial API or reuse license for its tables was found. Its `robots.txt` disallows `/dp-api/`. Its app terms forbid copying the app and reserve database rights. Calculated tables from that site are not stored in this project.

## Prokerala

Sources: [terms](https://api.prokerala.com/tos), [pricing](https://api.prokerala.com/pricing), [credit table](https://api.prokerala.com/api-credits), [OpenAPI](https://api.prokerala.com/spec/astrology.v2.yaml), [getting started](https://api.prokerala.com/getting-started).

Authentication is OAuth client credentials against `https://api.prokerala.com/token`. The client secret stays on the server.

Published plans on 14 October 2026:

| Plan       | Price                                        | Credits per month      | Rate limit            |
| ---------- | -------------------------------------------- | ---------------------- | --------------------- |
| Free       | $0                                           | 5,000                  | 5 requests per minute |
| Ruby       | $19 per month, shown as discounted from $39  | 100,000                | 60 per minute         |
| Emerald    | $49 per month, shown as discounted from $99  | 350,000                | 120 per minute        |
| Sapphire   | $99 per month, shown as discounted from $199 | 1,000,000              | 300 per minute        |
| Enterprise | Quote, Ennexa Technologies Pvt. Ltd.         | Above the listed plans | Not published         |

Credits reset each billing cycle and do not roll over. Unused credits are non-refundable. Fees can change on 30 days' notice, taking effect at the next renewal.

Published credit costs for the operations this app would use:

| Operation                           | English | Other languages                                                                                            |
| ----------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------- |
| Basic Panchang                      | 10      | 20                                                                                                         |
| Advanced Panchang                   | 100     | 200                                                                                                        |
| Inauspicious period                 | 50      | 100                                                                                                        |
| Auspicious period                   | 50      | 100                                                                                                        |
| Daily prediction, basic or advanced | 250     | The daily operation's parameter list in the OpenAPI excerpt has `datetime` and `sign`, not a language code |

The credit page lists basic Panchang languages as `en`, `hi`, `ta`, `ml`, and `te`. The shared `la` parameter text says the endpoint supports more than 20 languages, including Gujarati, Kannada, Bengali, Marathi, and Punjabi, and points at a language list. Those two statements disagree. A validation call has to record which languages return translated names. Missing languages stay in English identifiers from the normalized schema, not in machine-translated religious names.

Basic Panchang is enough for the five limbs and for sunrise and sunset. Rahu Kaal is on the inauspicious-period operation, so a city-date that needs Rahu Kaal is 60 English credits, not 10. Advanced Panchang costs 100 English credits and includes both the limbs and the inauspicious periods in one body. The MVP quote should use 60 credits per city-date unless a test shows the separate calls disagree.

Worked example, not a quote: 60 cities, once a day, 60 English credits each, 30 days, is 108,000 credits. That is above the Ruby allotment and inside Emerald. Computing one uncached advanced response per user per day will exhaust a listed plan as soon as daily users are in the thousands. The 24-hour cache is what makes the listed plans plausible. The terms also forbid a permanent archive and a competing database, so the cache is a serving cache, not a second ephemeris.

The terms say astrology results differ by tradition, ayanamsa, house system, coordinates, and time zone, and they disclaim accuracy and uninterrupted service. There is no published ephemeris name, solar-limb rule, or elevation rule on the Panchang operation. Those gaps are why the test specification exists. They are not, by themselves, a reason to skip the candidate.

The daily horoscope sample is interpretive prose. The app's content rule forbids showing that prose until it is reviewed. The cache and deletion rules make a review archive difficult. Advertisements around an application are allowed, so a later ad decision is not blocked by this clause. Selling the API onward is blocked.

## Drik Panchang

Sources: [sunrise method](https://www.drikpanchang.com/panchang/sunrise/panchang-sunrise.html), [settings](https://www.drikpanchang.com/settings/drikpanchang-settings.html), [drik and vakya](https://www.drikpanchang.com/tamil/info/thiruganita-versus-vakyam-panchangam.html), [about](https://www.drikpanchang.com/contribution/why-contribute-drik-panchang.html), [app terms](https://www.drikpanchang.com/contactus/privacy-policy/app/dp-apps-terms-and-conditions.html), [privacy policy](https://www.drikpanchang.com/contactus/privacy-policy/dp-privacy-policy.html), [robots.txt](https://www.drikpanchang.com/robots.txt).

The site says its ordinary calculations use drik ganita, meaning modern planetary positions, and that Surya Siddhanta or vakya arithmetic is limited to Tamil and Bengali modes. It says the default sunrise is the upper limb with refraction, that the middle limb is an optional setting, and that elevation is off unless enabled. It says high latitudes where the Sun stays up are unsupported, and that daylight-saving time is applied for cities that use it. Those sentences are the useful part of the source.

The same site does not offer those tables under a license this app can accept. The app terms say the app, trademarks, copyright, and database rights remain with Drik Panchang, and they forbid copying, modifying, translating, or making derivative versions of the app. The about page says the site is free to visitors and funded by advertising and voluntary payments. Free for a visitor to read is not a grant to cache or resell. A search for a website terms page that authorizes reuse did not find one. The path guessed for a terms page returned HTTP 404.

Using the site as an oracle, including a private scrape of `/dp-api/`, is out of bounds. A person may read the method pages while writing the reference convention. The test log does not contain copied Drik rows.

## Swiss Ephemeris

Sources: [license overview](https://www.astro.com/swisseph/sweph_e.htm), [price](https://www.astro.com/swisseph/swephprice_i.htm), [professional contract, edition September 2026](https://www.astro.com/swisseph/secont_e_2609.pdf), [programming documentation](https://www.astro.com/swisseph/swisseph.htm).

The developer chooses AGPL or the professional contract before distributing an app or opening a public service. AGPL would cover the whole project that uses the library, including a server. This app is a closed-source Android product, so the professional contract is the license that fits.

The September 2026 contract costs CHF 700 for an unlimited number of projects developed or maintained by the licensee. It lasts six years and then must be renewed, or use in distributed software and web services stops. The software is downloaded from the public GitHub repository after the contract is paid. Correctness is not guaranteed. Support is the public mailing list. Copyright notices in the library stay in place. The authors' names are not used in promotion without written permission.

If this project later exposes calculation as an API to another business, that business needs its own Swiss Ephemeris license, and Astrodienst must be told. An internal server that calculates for this app is covered. A white-label endpoint for other companies is not.

The library documents sidereal modes. Lahiri is mode 1. Lahiri-ICRC is a different mode. Appendix E of the programming documentation compares Lahiri values with the Indian Astronomical Ephemeris and reports sub-arcsecond to tenths-of-an-arcsecond differences for several epochs, with some editions that the authors could not reproduce exactly. That is evidence about the ayanamsa function. It is not evidence about a finished tithi.

Rise and set are a documented function with caller-selected flags. The Panchang rules in the test specification are not inside the library. Shipping Swiss Ephemeris without those reviewed rules would invent the religious layer, which this project forbids.

The professional license is the fallback because the method is published and the commercial terms are a one-time contract with a known renewal date. It is slower to reach a correct Panchang than a hosted API, and it still needs the test specification.

## DivineAPI

Sources: [terms](https://divineapi.com/terms-service), [pricing](https://divineapi.com/pricing), [Panchang product page](https://divineapi.com/indian-astrology/panchang-api), [refund policy](https://divineapi.com/refund-and-cancellation-policy).

The terms grant, during an active paid subscription, the right to publish, store, cache, white-label, translate, and monetize API-generated content in the customer's own app. User-facing attribution is not required. After the subscription ends, previously published fixed copies may be kept, and new daily content may not be generated from the cache. The endpoints themselves may not be resold. Reverse engineering the calculation is forbidden, which also means a customer cannot audit the method from the response stream.

The pricing page describes a 14-day trial that requires a card, and a Panchang tier at $19 per month for 100,000 requests, with a higher tier at $79 per month for 600,000 requests. A support article quotes rupee prices and different discount percentages. Those pages were not reconciled. GST treatment should be read on the invoice.

The product page says calculations use the Swiss Ephemeris and names Lahiri on the pricing feature list. It does not, in the pages read, state the request field for ayanamsa, the solar limb, or elevation. It also says timings match what a traditional priest would publish. That sentence is advertising. It is not a test result.

The Swiss Ephemeris contract says a licensee who provides an API to another business must require that business to hold its own license. If DivineAPI's service is that kind of API, this project may still need its own Swiss Ephemeris license. That question has to be answered in writing by DivineAPI and, if they cannot answer it, by Astrodienst, before DivineAPI replaces Prokerala.

The uptime clause is a 99.9% monthly target with exclusions. Standard-plan remedy language points at an Enterprise MSA for contractual credits. Support hours are weekdays 09:00–18:00 IST.

DivineAPI is the stronger candidate if the product priority becomes reviewed, translatable horoscope prose under a subscription. It is the weaker candidate for the Panchang MVP because the calculation convention is less fully published than Prokerala's request parameters, and the ephemeris license chain is unresolved.

## Vedika and XALEN

Sources: [Panchang page](https://vedika.io/panchang-api), [pricing](https://vedika.io/pricing), [terms](https://vedika.io/terms), [commercial license file](https://github.com/vedika-io/xalen-ephemeris/blob/main/COMMERCIAL_LICENSE.md).

The Panchang page says production is wallet-priced, that a free sandbox returns mock data, and that the engine is "XALEN Ephemeris" from 3000 BCE to 3000 CE with accuracy to 0.001 degrees. It also says the same ephemeris is used by professional astrologers and astronomical institutions. No institution is named. Mock sandbox data cannot be used in the accuracy test.

The pricing page lists Panchang operations at $0.0100 in a "catalog snapshot" and describes several overlapping per-query ranges. The terms page retrieved describes chart and report services, key secrecy, and plan limits. It does not contain a content license comparable to DivineAPI's section 4.

The XALEN commercial-license file says the library is Apache-2.0, with optional paid tiers for attribution waiver, warranty, and support. The README URL for that repository returned an empty document during this review. An Apache-2.0 engine with a published method would be a serious fallback. An empty method document is not enough to accept it. Vedika is out of the MVP until a calculation note states ayanamsa, limb, refraction, and elevation, and until production responses, not mock responses, pass the test specification.

## Single-provider risks

1. **The religious result and the astronomical result are different products.** A correct Moon longitude can still feed an undocumented sunrise rule and move Ekadashi to the next civil date. The test separates those layers.
2. **Cache limits.** Prokerala's 24-hour cap and deletion-on-termination rule mean a multi-day offline phone cannot legally keep a month of their responses unless they agree in writing. The MVP cache is one civil day for the cities users actually request.
3. **Credit and rate cliffs.** A client that calls the API on every screen open will pass the free tier and then the paid tier. The server deduplicates by city, date, ayanamsa, and convention.
4. **Language gaps.** Five of the app's ten languages are missing from the credit-page Panchang list. Unreviewed machine translation of tithi names is not a fallback.
5. **Horoscope prose is copyrighted text.** Display, translation, and ads are separate grants. Prokerala grants display and ads. It does not expressly grant translation or a review archive.
6. **No accuracy warranty.** Prokerala, Swiss Ephemeris, and DivineAPI each disclaim fitness of the calculation. The app's UI has to keep a short statement of the convention after a provider is connected.
7. **Uptime.** Prokerala offers no SLA on the public terms. A failed call stays an error on screen. The app must not substitute a different provider's number silently, and it must not invent one.
8. **License stack.** A hosted API that embeds Swiss Ephemeris can impose a second license on the customer. That is a condition of using DivineAPI, and it should be asked of Prokerala as well because their ephemeris is unpublished.
9. **Price changes.** Both hosted vendors reserve a notice period and then a new price. The fallback library has a six-year renewal instead of a monthly bill.
10. **Festival rules are not Panchang elements.** Amanta and Purnimanta, and Tamil or Bengali traditional arithmetic, move festival dates without either calculator being "wrong". The test records those rows instead of forcing one regional calendar.

## Approval gate

Before any secret, SDK, or paid call is added:

1. Accept Prokerala terms for a named plan, or reject them and switch to the Swiss Ephemeris contract.
2. Confirm in writing whether a 24-hour server cache of city-date Panchang responses is the full storage right, and whether the test log may be kept.
3. Ask which ephemeris, solar limb, refraction, and elevation the Panchang operation uses.
4. Run [`PANCHANG_TEST_SPEC.md`](PANCHANG_TEST_SPEC.md) and keep the pass or fail log.
5. Leave horoscope text unavailable under this approval. A text vendor is a second decision.
6. Keep the client free of the provider secret, birth fields, and a permanent copy of provider rows.

Until that gate is passed, `getPanchang` continues to ignore coordinates and return `status: 'unavailable'`.
